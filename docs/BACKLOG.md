## 多团队成员关系（未来优化）

- **优先级**：Medium
- **来源**：Issue #64 / PR #72 Phase 2 业务决策

### 当前已支持的假设

当前产品按**单一团队**建模：所有 `Member`、`Buddy`、`Leader` 用户属于同一个团队；`Admin` 的只读范围与 `Leader` 相同，均为全部 `Member` 角色用户，不享有额外的隐藏范围。`buddy_relationship` 仅表示“哪位 Buddy 负责辅导/复核哪位 Member”，不定义团队归属。

### 当前限制

- 没有 `team`、`team_membership` 或 `leader_relationship` 等业务模型。
- 没有多团队隔离或跨团队拒绝机制。
- Leader/Admin 的“团队范围”目前退化为全部 Member 用户；产品层面尚未区分“我的团队”与“其他团队”。

### 未来工作

1. 明确多团队业务模型（团队、团队成员、Leader 归属）。
2. 新增对应数据表/迁移，并补充历史数据回填策略。
3. 更新 Leader/Admin 授权层，使团队范围来自显式关系而非角色全集。
4. 补充跨团队拒绝测试（Leader A 看不到 Leader B 团队成员）。
5. 复核相关查询与索引，确保按团队过滤后仍满足性能要求。
6. 用户验收测试（UAT）确认多团队隔离行为。

### 注意事项

**不要声称当前已实现多团队隔离。** 在 Issue #64 范围内，明确接受单团队 MVP 语义。
